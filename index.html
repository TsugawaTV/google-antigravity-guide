第1章：Antigravity 概要とアーキテクチャ

1.1 Agent-First 開発思想の革命（Cursor / Copilot との違い）

Google Antigravity は、従来の「コード補完型（Copilot）」や「サイドバー質問型（Cursor初期モデル）」とは一線を画す、「完全自律完走型（Agent-First）」のソフトウェアエンジニアリングプラットフォームです。

開発者が大まかなゴールや要件を渡すだけで、エージェントはコードベース全体の構造を自動探索し、実装計画を立案・提案した上で、ファイル編集、ビルド実行、テスト修正、さらにはヘッドレスブラウザでのUI検証まで自律的にループを回して完遂します。

比較項目 従来のAI補完 (Copilot等) インタラクティブIDE (Cursor等) Google Antigravity
主導権 人間（1行ずつTab補完） 人間（指示と承認の反復） エージェント（自律ループ + レビュー駆動）
実行能力 エディタ内補完のみ ファイル変更 + 単発コマンド実行 全ツール協調（Subagents, Browser, MCP, Cron）
検証プロセス 人間が手動実行・検証 ターミナル結果を人間が確認 自律テスト実行・ブラウザ録画・自己修復
コンテキスト管理 開いているタブのみ RAG + @codebase 埋め込み Dynamic Subagents で長大調査を隔離・保護

1.2 プロダクトラインナップの役割と使い分け

Antigravity は単一のツールではなく、開発者のワークスタイルに合わせて4つの形態（Surfaces）がシームレスに提供されています。すべての形態で同一の Agent Engine と Customization（Rules / Skills / MCP）が共有されます。

Antigravity 2.0 (Desktop App)

白ロゴ / 司令塔
Multi-Agent Control Center

独立したデスクトップアプリ。複数のプロジェクトやブランチを並行して管理し、Auxiliary Paneで複数サブエージェントやバックグラウンドタスク、ブラウザ検証の録画をリアルタイム監視可能。

最適用途: プロジェクト全体の司令塔、複数エージェント並行作業、非同期タスク監視

Antigravity IDE

黒ロゴ / エディタ
VS Code Based AI-First Editor

エディタネイティブの統合開発環境。Ctrl+I のインライン指示、次世代Tab補完（Supercomplete）、関数上部のCode Lensから直接エージェントを呼出可能。

最適用途: 日常的なコーディング、インラインリファクタリング、手動編集併用

Antigravity CLI (agy)

Lightweight Terminal TUI & Headless

ターミナル上で超高速に起動するTUI。リモートSSH環境やヘッドレスCI/CD環境、Dockerコンテナ内でも動作し、OSキーリングまたはAPIキーでシームレスに認証可能。

最適用途: SSHサーバー、CI/CDパイプライン自動化、ターミナル愛好者

Google Antigravity SDK

Python Programmatic Library

pip install google-antigravity で導入。自作Pythonプログラムからエージェントを直接生成・制御し、独自のカスタムツールやパイプラインに組み込み可能。

最適用途: 自社エージェント開発、自動テストスクリプト、バッチ処理組み込み
ベストプラクティス：「Keep Both（両方併用）」ワークフロー
公式およびエキスパート開発者は、白ロゴ（2.0 司令塔）と黒ロゴ（IDE）の併用を強く推奨しています。
・2.0 司令塔: バックグラウンドで複数の自律タスク（新機能実装・テスト作成・ドキュメント更新）を走らせ、進捗をリアルタイム監視。
・IDE: 司令塔が作成したブランチやファイルをリアルタイムで確認しながら、インライン補完で精密な調整を行う。

第2章：コア概念と「Artifacts（成果物）」システム

2.1 Artifacts システムの仕組みとライフサイクル

Antigravity の最大の特徴は、チャット内の流れていくテキストではなく、専用ディレクトリ（~/.gemini/antigravity/brain/<conversation-id>/）に構造化された「Artifacts（成果物ドキュメント）」を生成・維持管理する点にあります。

implementation_plan.md

実装前に作成される技術仕様書。変更対象ファイル一覧、設計方針、ユーザー確認事項（Open Questions）、検証手順が記載され、人間の承認待ち状態を生成します。

walkthrough.md

作業完了時に作成される報告書。実施した変更の差分要約、実行した単体テスト・E2Eテスト結果、スクリーンショットや録画へのリンクが記録されます。

transcript.jsonl

エージェントの思考プロセス（Thinking）、ツール呼び出し引数、標準出力の全履歴を記録したJSON Lines形式の監査ログ。いつでも過去の意思決定を逆引き可能。

scratch/ ディレクトリ

一時的なスクリプトや実験用データ、調査用の一時ファイルを保存する隔離領域。ワークスペースのGitツリーを汚さずに試行錯誤を行えます。

2.2 レビュー駆動開発（Review-Driven Development: RDD）

AIエージェントによるコード破壊事故を防ぐため、Antigravity は「計画フェーズ（Planning Mode）」と「実行フェーズ（Execution Mode）」を厳格に分離する「レビュー駆動開発（RDD）」を採用しています。

1. Research
コード探索・Web検索
※ファイル変更禁止
2. Implementation Plan
設計書・変更予定を提示
※人間が確認・承認
3. Autonomous Exec
編集・ビルド・テスト自律実行
※テスト通過まで自己修正
4. Walkthrough
検証エビデンス提示
※最終コミット完了
RDDの真髄：Artifacts インラインコメント機能
提示された implementation_plan.md やコードDiff画面では、修正したいテキスト範囲をマウスでドラッグ選択して「Add Comment」をクリックすることで、該当行に直接インライン修正指示（例: 「ここはJWTではなくセッションCookieで実装して」）を書き込めます。「Submit Feedback」を押すだけで、エージェントは全体の文脈を保ったままピンポイントに計画を書き直します。

2.3 Local Mode vs New Worktree Mode

エージェントにタスクを依頼する際、実行環境の分離レベルを2つのモードから選択できます。

Local Workspace Mode

デフォルト

現在開いているワーキングディレクトリ上で直接ファイルを編集します。エディタの保存やHot Reloadが即座に反応し、開発者がリアルタイムに差分を確認できます。

  • メリット: 即時フィードバック、シンプルなタスク向け
  • 注意点: 人間の未コミット作業と競合する可能性あり

New Worktree Mode

推奨: 重厚タスク

Git Worktree 機構を用いて、裏側で独立したワークスペースディレクトリを瞬時にクローン作成。メインの作業ディレクトリを一切汚さずにエージェントが自律作業を行います。

  • メリット: メイン作業と完全並行稼働、失敗しても1秒で破棄可能
  • 完了時: テスト通過後にワンクリックでブランチマージ

2.4 推論努力度（Reasoning Effort）の設定指針 & 判断マトリクス

Gemini 3.7 Flash や Claude 4.6 (thinking) などの推論モデルでは、タスクの難易度に応じて「Reasoning Effort（推論の深さ・思考時間）」を調整することで、コストと速度、解答精度のトレードオフを最適化できます。

Low（低推論）

思考ステップを最小化し超高速に応答。定型的なボイラープレート生成、変数名のリネーム、単純なCSS調整に最適。

目安: 1〜3秒で即座に応答
Medium（標準推論）

バランスの取れた標準設定。一般的なWeb機能開発、API統合、単体テストスイートの自動作成、コードレビューに最適。

目安: 5〜15秒の論理検証
High（深層推論）

思考トークンを最大限活用。難解なRace Condition調査、大規模分散アーキテクチャ設計、数学的アルゴリズム導出に必須。

目安: 30秒〜数分のディープ思考
開発シーン・タスク種別 推奨設定 推奨モデル 選定理由
Tab補完・インライン微修正 Low Gemini 3.7 Flash 打鍵速度に追従する低レイテンシが必要なため
通常機能実装・テスト作成 Medium Gemini 3.7 Flash 適度な思考深度と高速なツール呼び出しのバランス
大規模リファクタ・型エラー連鎖 High Claude 3.7 Sonnet (thinking) 数十ファイルに跨る依存関係の深層推論が必要なため

/grill-me

要件定義・アライメント・インタビュー

実装を開始する前に、エージェント側から開発者に対して徹底的に質問攻めを行い、仕様の曖昧さ、エッジケース、セキュリティ要件、データモデルの設計意図を洗い出します。

使用推奨シーン: 新規マイクロサービスの設計、認証認可の仕様策定、複雑なビジネスロジックの導入時。曖昧なまま着手して後から全書き換えになるリスクを完全に防ぎます。

エージェントに対して「〇分後」の一時タイマー通知や、「毎朝9時」「毎時0分」といったCron形式のスケジュールタスクを設定できます。

Cron定期ジョブ例

パラメータ名 型 / 設定値 動作説明
DurationSeconds 整数（例: 600） ワンショットタイマーの待機秒数。CronExpressionと排他。
CronExpression 文字列（例: */5 * * * *） 標準5フィールドCron式。定期リピートタスクに指定。

IsDaemon true | false true は現在のチャット完了後もバックグラウンドで永続常駐。

4.1 Dynamic Subagents（動的サブエージェント）とコンテキスト保護

大規模なリポジトリで数百個のファイルを検索・閲覧すると、メインエージェントのコンテキストウィンドウが不要なログで溢れ（コンテキスト汚染）、推論精度が急激に低下します。

Antigravity は invoke_subagent ツールにより、一時的な子エージェント（Subagent）をオンデマンドで生成。子エージェントは隔離されたコンテキストで膨大な探索を行い、最終的な「要約された結論」だけを親エージェントに返却します。

4.2 Asynchronous Task Management & システムトレイ常駐

開発サーバーの起動（npm run dev）や重いビルド処理、Dockerの起動などの長時間プロセスは、非同期バックグラウンドタスクとして実行されます。

Reactive Wakeup（リアクティブ起動）& タイマー監視:
エージェントは無駄にCPUを消費してポーリングを行いません。タスク完了やサブエージェントからのメッセージを受信した瞬間にイベント駆動で自動再開します。また、長時間の探索がスタックしないよう、schedule ツールによる「90秒チェックイン（Heartbeat監視）」を設定し、応答がない場合の自律リカバリを担保します。
OSタスクトレイ常駐 & 並列稼働エージェント数の可視化

Antigravity はバックグラウンドで `/goal` や深夜の自動テストスイートが走っている際、Windows の通知領域（タスクトレイ）/ macOS メニューバーに常駐します。アイコン上に「現在並行稼働しているエージェント数（例: 3）」がバッジ表示され、クリック1発で対象の会話や録画ビューへ即座に復帰できます。

4.3 JSON Lifecycle Hooks（ライフサイクルフック）

プロジェクト内の .agent/hooks.json で定義することで、エージェントの特定イベント（ツール実行前、ターン開始時、完了時）にシェルスクリプトやバリデータを自動介入させることができます。

フックイベント名 発火タイミング 代表的な活用ユースケース
pre_tool_execution ツール実行直前（ブロック可） 危険コマンド（rm -rf / drop db）の静的検査と遮断。
post_file_write ファイル保存直後 Prettier / Biome / ESLint の自動フォーマッター即時実行。
on_goal_complete /goal タスク完走時 Slack / Discord / Teams への完了通知 Webhook 呼出。
設定例: .agent/hooks.json
{
  "hooks": {
    "pre_tool_execution": [
      {
        "matcher": "run_command",
        "condition": "command.includes('rm -rf') || command.includes('drop database')",
        "action": "block_and_alert",
        "message": "危険なコマンドが検出されたため実行をブロックしました。"
      }
    ],
    "post_file_write": [
      {
        "matcher": "*.ts|*.tsx|*.js",
        "action": "execute_script",
        "command": "npx prettier --write {{file_path}}"
      }
    ]
  }
}

4.4 セキュリティ・権限ポリシー & カーネルサンドボックス

Antigravity は、エージェントによる偶発的なファイル破壊や機密情報漏洩を防ぐため、すべての敏感な操作を action(target) 形式でモデル化し、3段階のアクセスリスト（Deny / Ask / Allow）とOSカーネルレベルのサンドボックスで評価します。

1. Deny（恒久ブロック）

即座に実行を遮断。.env、SSH秘密鍵、.git/ への書き込み、sudo、rm -rf 等を恒久的に防壁化。

2. Ask（手動承認要求）

実行前にユーザーへ承認ダイアログを表示。未設定のコマンドや外部URLアクセス、破壊的マイグレーション等の安全弁として機能。

3. Allow（自動承認）

プロンプトなしで自律実行を許可。git コマンド、npm test、ワークスペース内 src/ へのファイル書き込みを承認。

アクション ターゲット構文の例 既定値 説明 & 暗黙ルール
read_file read_file(/path), read_file(*) Ask（Workspace内はAllow） ファイルの読み取り権限。
write_file write_file(src/), write_file(.git/) Ask（Workspace内はAllow） ファイルの新規作成・編集。※write許可時は自動でreadも許可
command command(git), command(npm run (build|test)) Ask プレフィックスや正規表現で端末コマンドを制御。
read_url read_url(google.com), read_url(*) Ask HTTPリクエストによる外部ドキュメント取得。
execute_url execute_url(localhost), execute_url(aws.amazon.com) Ask ブラウザ操作（クリック・フォーム入力）の接続先ドメイン制限。
unsandboxed unsandboxed(docker), unsandboxed(*) Ask カーネルサンドボックス外でのコマンド直接実行。
mcp mcp(postgres/*), mcp(github/create_pr) Ask MCPツールの個別またはサーバー単位の実行制御。
権限設定の推奨テンプレート（Allow / Deny / Ask）:
# Allow（自動承認）
command(git)
command(npm run (build|lint|test))
write_file(src/)
write_file(tests/)
read_url(google.com)
read_url(github.com)
mcp(linter/*)

# Deny（恒久ブロック - セキュリティ絶対防衛）
command(rm -rf)
command(sudo)
command(curl .*)
write_file(.git/)
write_file(.env*)
write_file(/home/user/.ssh)

# Ask（危険度が高い操作は手動承認）
command(*)
execute_url(aws.amazon.com)
mcp(postgres/execute_mutation)

OSカーネルレベルのターミナルサンドボックス機構

Antigravity のサンドボックスは、エージェントが実行する端末コマンドをOSカーネル層で物理隔離します。

  • macOS: Apple Seatbelt (sandbox-exec) によりワークスペース外への書き込みをカーネルレベルで遮断。
  • Linux: nsjail によるプロセス分離・ファイルシステムマウント隔離・リソース制限。
  • ネットワーク隔離: Sandbox Allow Network: OFF に設定することで、read_url で許可したドメイン以外の全アウトバウンド通信を遮断。
CLI YOLO モード（--dangerously-skip-permissions）の警告:
全確認プロンプトをスキップする YOLO 起動は、Docker コンテナや隔離 VM などの使い捨て環境でのみ自己責任で使用してください。ホストマシンの本番ディレクトリでは絶対に使用しないでください。

5.3 Google Antigravity Python SDK 実践プログラミング

自社スクリプトやCI/CDパイプラインからプログラムでエージェントを召喚・制御する完全コード例です。思考ストリーミング、ツール呼び出し監視、カスタムツールの付与が可能です。

Python SDK 実装例 (main.py)
import asyncio
import sys
from google.antigravity import Agent, LocalAgentConfig, CapabilitiesConfig

async def run_autonomous_pipeline():
    # 1. エージェントの構成設定（書き込み権限・コマンド実行ツールを有効化）
    config = LocalAgentConfig(
        system_instructions="あなたは最先端のフルスタックエンジニアです。テスト駆動で堅牢なコードを作成してください。",
        capabilities=CapabilitiesConfig(
            enable_file_write=True,
            enable_run_command=True,
        ),
        model="gemini-3.7-flash",
    )

    # 2. 非同期コンテキストマネージャーでエージェントを起動
    async with Agent(config) as agent:
        print("=== Antigravity Agent 起動中 ===")
        
        # チャット指示を送信
        response = await agent.chat(
            "FastAPI を使ったシンプルな認証API（/login, /me）を作成し、pytest の単体テストを作成して実行してください。"
        )

        # 思考（Thinking）ログのリアルタイム監視
        async for thought in response.thoughts:
            print(f"[\033[94mThinking\033[0m] {thought}")

        # ツール呼び出しの監視
        async for tool_call in response.tool_calls:
            print(f"[\033[92mTool Executed\033[0m] {tool_call.name} (args: {tool_call.args})")

        # 最終レスポンストークンのストリーミング出力
        print("\n=== エージェント最終報告 ===")
        async for token in response:
            sys.stdout.write(token)
            sys.stdout.flush()
        print("\n")

if __name__ == "__main__":
    asyncio.run(run_autonomous_pipeline())

WordPress プラグイン開発の完全手順（セキュリティ5原則・WPCS規約）

公式セキュリティ完全網羅

WordPress 公式セキュリティ原則（「データを信用しない」「WordPress APIに頼る」）に基づき、nonce検証・サニタイズ・エスケープ・権限チェック・プリペアドステートメントを100%実装する完全手順です。

WordPress セキュリティの5原則（必須実装コード集） 

<?php
// 1. 直接アクセスの即時遮断（全PHPファイルの先頭に記述）
if ( ! defined( 'ABSPATH' ) ) {
    exit;
}

// 2. Nonce による CSRF 対策（フォーム出力 & 受信検証）
// 【フォーム出力時】
wp_nonce_field( 'my_lead_action', 'my_lead_nonce' );

// 【受信検証時: WPCS準拠の unslash + sanitize + verify】
if ( ! isset( $_POST['my_lead_nonce'] ) || ! wp_verify_nonce( sanitize_text_field( wp_unslash( $_POST['my_lead_nonce'] ) ), 'my_lead_action' ) ) {
    wp_die( esc_html__( 'セキュリティチェックに失敗しました。', 'my-plugin' ) );
}

// 3. 入力値のサニタイズ（入力時・型に応じた関数を使用）
$name  = sanitize_text_field( wp_unslash( $_POST['name'] ?? '' ) );
$email = sanitize_email( wp_unslash( $_POST['email'] ?? '' ) );
$msg   = wp_kses_post( wp_unslash( $_POST['message'] ?? '' ) );
$qty   = absint( $_POST['qty'] ?? 0 );

// 4. 出力のエスケープ（出力直前でコンテキストに応じた関数を使用）
echo esc_html( $name );                                              // テキスト出力
echo '<a href="' . esc_url( $user_url ) . '">' . esc_html__( '詳細', 'my-plugin' ) . '</a>'; // URL & 翻訳テキスト
printf( '<input value="%s" />', esc_attr( $name ) );               // HTML属性値内

// 5. 権限チェック (Capability Check)
if ( ! current_user_can( 'manage_options' ) ) {
    wp_die( esc_html__( 'この操作を実行する権限がありません。', 'my-plugin' ) );
}

// 6. プリペアドステートメントによる SQL インジェクション完全防止
global $wpdb;
$table_name = $wpdb->prefix . 'my_leads';
$wpdb->insert(
    $table_name,
    array( 'name' => $name, 'email' => $email, 'created_at' => current_time( 'mysql' ) ),
    array( '%s', '%s', '%s' )
);
$results = $wpdb->get_results(
    $wpdb->prepare( "SELECT * FROM {$table_name} WHERE email = %s", $email )
);

エージェント用ワークスペースルール（.agents/rules/wordpress-security.md） 

# WordPress プラグイン開発セキュリティ規約

- すべてのユーザー入力は sanitize_* 関数でサニタイズすること。
- すべての出力は esc_html / esc_attr / esc_url / wp_kses_post でエスケープすること。
- 状態変更リクエストには必ず nonce を付与し wp_verify_nonce で検証すること。
- 権限チェックは current_user_can('manage_options') 等で実施すること。
- SQL は必ず $wpdb->prepare() を使用し、直接クエリ展開を禁止すること。
- ユーザー向け文字列はすべて __() / _e() / esc_html__() でラップし i18n 対応すること。
- $_GET / $_POST の直接参照を禁止し、必ず wp_unslash() とサニタイズを併用すること。
- 直接アクセス防止コード `if ( ! defined( 'ABSPATH' ) ) exit;` を全PHPファイルの先頭に記述すること。

第7章：プロンプトエンジニアリング＆トラブルシューティング

7.1 自律エージェントを迷走・暴走させない「制約条件（Constraints）」の極意

自律型エージェントに指示を出す際、「何をすべきか（Do）」だけを書くと、エージェントは意図しないライブラリを勝手にインストールしたり、既存の重要なコードを書き換えてしまうことがあります。

成功率を最大化する鍵は「何をしてはならないか（Negative Constraints）」と「終了判定基準（Definition of Done: DoD）」を明記することです。

❌ 失敗しやすい曖昧な指示
「ユーザー認証機能を作って、動くようにしておいて。」
⭕ 成功するプロフェッショナル指示
/goal
NextAuth.js (v5) を使ったGitHub OAuth認証を導入してください。

【制約条件（Constraints）】
- 既存の Prisma スキーマにある User モデルを変更せず、Account モデルのみを追加すること。
- 新規の外部UIコンポーネントライブラリは追加せず、既存の Tailwind クラスを使用すること。
- 未認証ユーザーが /dashboard にアクセスした際は自動で /login にリダイレクトすること。

【完了条件（Definition of Done）】
- `npm run build` が型エラーなしで完了すること。
- `tests/auth.test.ts` を作成し、モック認証テストが全件パスすること。
